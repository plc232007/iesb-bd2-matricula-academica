Ambiente Docker

Base para a demonstração ao vivo
Pedido: "Demonstração ao vivo: o banco rodando no ambiente Docker [...] Não é permitido vídeo gravado ou captura de tela." E o README tem que subir o banco do zero.
compose.yaml
services:
  postgres:
    image: postgres:16
    environment:
      POSTGRES_USER: bd2
      POSTGRES_PASSWORD: bd2
      POSTGRES_DB: matricula
    ports:
      - "${POSTGRES_PORT:-5432}:5432"
    volumes:
      - bd2_dados:/var/lib/postgresql/data
      - ./:/docker-entrypoint-initdb.d:ro
Como funciona
  • A pasta do projeto é montada em /docker-entrypoint-initdb.d. Na primeira subida, com o volume vazio, a imagem do Postgres roda sozinha todos os .sql dessa pasta em ordem alfabética, de 01 até 07. Por isso os arquivos são numerados.
  • Se o volume bd2_dados já tiver dados, ela pula essa etapa e mostra Skipping initialization no log. Para recriar tudo: docker compose down -v e depois docker compose up -d.
  • ${POSTGRES_PORT:-5432} quer dizer "use a variável, ou 5432 se ela não existir". Quem já tem um Postgres instalado na máquina cria um .env com POSTGRES_PORT=5435. A porta de dentro do container continua sendo 5432.
  • Testamos com PostgreSQL 16 e 17. O 17 é o do ambiente oficial da disciplina.

DDL e restrições de integridade

Frente: Modelagem Física e Desempenho · 01_ddl.sql (Marco 1) e 07_testes_integridade.sql
Pedido: "Implementação do DDL completo: tabelas, tipos, domínios, chaves e todas as restrições de integridade". Na demonstração: "as restrições de integridade em funcionamento".

O DDL é do Marco 1. No Marco 2 foram duas coisas: uma correção no gatilho e um script que tenta quebrar cada regra para mostrar o banco recusando.

As restrições que mais caem na arguição

01_ddl.sql
-- DOMÍNIO: tipo base + regra. Toda coluna nota_t herda o CHECK.
CREATE DOMAIN nota_t AS numeric(4,2) CHECK (VALUE >= 0 AND VALUE <= 10);

-- COLUNA GERADA: o banco calcula, ninguém consegue gravar valor errado
ch_total smallint GENERATED ALWAYS AS (ch_teorica + ch_pratica) STORED,

-- ÍNDICE ÚNICO PARCIAL: no máximo um currículo ativo por curso
CREATE UNIQUE INDEX uq_tb_curriculo_ativo ON tb_curriculo (curso_id) WHERE ativo;

-- EXCLUDE: a mesma sala não pode ter dois horários que se cruzam no mesmo dia
CONSTRAINT ex_tb_sala_ocupada
    EXCLUDE USING gist (
        sala_id    WITH =,
        dia_semana WITH =,
        (timerange(horario_inicio, horario_fim)) WITH &&
    )
Como funciona
  • Domínio: a regra fica num lugar só. Se o limite da nota mudar, muda no domínio e vale para A1, A2 e A3.
  • Coluna gerada: ch_total e media_final são calculadas pelo banco a cada INSERT/UPDATE. Tentar gravar nelas dá erro, então nunca ficam fora de sincronia.
  • Único parcial: só as linhas com ativo = true entram no índice. Dentro delas o curso_id não pode repetir, e currículos antigos (inativos) podem existir à vontade.
  • EXCLUDE é um UNIQUE generalizado. Em vez de proibir linhas iguais, proíbe linhas que se sobrepõem: mesma sala (=), mesmo dia (=) e intervalos que se cruzam (&&). Usa índice GiST, e a extensão btree_gist é o que permite misturar = de inteiro com && de intervalo no mesmo índice.

Correção no gatilho de vagas

01_ddl.sql
CREATE OR REPLACE FUNCTION fn_tb_valida_vaga() RETURNS trigger
LANGUAGE plpgsql
SET search_path = academico, public   -- linha nova do Marco 2
AS $$
...
    SELECT count(*) INTO v_ocupadas
      FROM tb_matricula_aluno
     WHERE turma_id = NEW.turma_id
       AND status   = 'MATRICULADO'
       AND matricula_aluno_id <> COALESCE(NEW.matricula_aluno_id, -1);

    IF v_ocupadas >= v_vagas THEN
        RAISE EXCEPTION 'Turma % sem vagas (% de %)', NEW.turma_id, v_ocupadas, v_vagas
              USING ERRCODE = 'check_violation';
    END IF;
Como funciona

O gatilho roda na sessão de quem fez o INSERT. Quando testamos com o usuário usuario_secretaria, o search_path dele não tinha o schema academico e a matrícula falhava com relation "tb_turma" does not exist. Com o SET search_path na própria função, ela sempre procura as tabelas no lugar certo, seja quem for o usuário.

Testes que mostram as regras funcionando

07_testes_integridade.sql
-- 1) DOMÍNIO nota_t: nota maior que 10
DO $$
BEGIN
    UPDATE tb_historico SET nota_a1 = 11
    WHERE matricula_aluno_id = (SELECT min(matricula_aluno_id) FROM tb_historico);
    RAISE NOTICE 'FALHOU 1: aceitou nota 11';
EXCEPTION WHEN check_violation THEN
    RAISE NOTICE 'OK 1 (domínio nota_t): %', SQLERRM;
END $$;
Como funciona

São 10 blocos iguais a esse, um por regra: domínio, CHECK do CPF, CHECK entre duas colunas, UNIQUE, FK, EXCLUDE, pré-requisito de si mesma, único parcial, coluna gerada e o gatilho de vagas. Cada um tenta gravar um dado errado:

  • se o banco recusa, o erro cai no EXCEPTION e aparece OK n com a mensagem do Postgres;
  • se aceita, aparece FALHOU.

Um erro dentro de um bloco DO desfaz só o que o bloco fez, então nada fica gravado. Cada bloco captura um erro específico (check_violation, unique_violation...). Se o banco recusasse pelo motivo errado, o teste não esconderia isso.

Views e materialized view

Frente: Administração e Operação · 04_views.sql
Pedido: "Views (oferta, vagas, histórico) e uma materialized view de indicadores com política de atualização justificada".

View comum não guarda dados: é uma consulta salva com nome, que roda de novo a cada SELECT. Materialized view guarda o resultado em disco. A leitura fica rápida, mas o conteúdo só muda com REFRESH.

vw_oferta

string_agg((ARRAY['dom','seg','ter','qua','qui','sex','sab'])[th.dia_semana]
           || ' ' || to_char(th.horario_inicio, 'HH24:MI')
           || '-' || to_char(th.horario_fim, 'HH24:MI')
           || ' ' || s.codigo_sala,
           ', ' ORDER BY th.dia_semana)     AS horarios
FROM   tb_turma t
...
LEFT   JOIN tb_turma_horario th ON th.turma_id = t.turma_id
LEFT   JOIN tb_sala s           ON s.sala_id   = th.sala_id
Como funciona

Uma turma tem até 2 linhas de horário (ex.: segunda e quarta). O string_agg junta as duas num texto só, tipo seg 19:00-20:50 A101, qua 19:00-20:50 A101, e a view fica com uma linha por turma. O LEFT JOIN mantém na oferta a turma que ainda não tem horário cadastrado. Ela aparece com horarios = NULL em vez de sumir.

vw_vagas

count(m.matricula_aluno_id)              AS ocupadas,
t.vagas - count(m.matricula_aluno_id)    AS livres,
CASE WHEN count(m.matricula_aluno_id) >= t.vagas
     THEN 'LOTADA' ELSE 'COM VAGA' END   AS situacao
...
LEFT JOIN tb_matricula_aluno m ON m.turma_id = t.turma_id
                              AND m.status   = 'MATRICULADO'
Como funciona
  • Conta só MATRICULADO, a mesma regra do gatilho. Trancado e cancelado liberam a vaga.
  • O filtro de status fica no ON, e não no WHERE. No WHERE ele eliminaria as turmas sem matrícula, e o LEFT JOIN viraria um JOIN comum.
  • Usamos count(m.matricula_aluno_id), e não count(*), porque o count(*) contaria 1 numa turma vazia (a linha da turma com NULL do lado da matrícula).

vw_historico

CREATE OR REPLACE VIEW vw_historico WITH (security_invoker = true) AS
SELECT a.aluno_id, a.matricula, a.nome AS aluno, ...
       h.nota_a1, h.nota_a2, h.nota_a3, h.media_final, h.frequencia, h.situacao
FROM   tb_historico h
JOIN   tb_matricula_aluno m ON m.matricula_aluno_id = h.matricula_aluno_id
JOIN   tb_aluno a           ON a.aluno_id           = m.aluno_id
...
Como funciona

Este é o detalhe mais importante das views. Por padrão, uma view lê as tabelas com a permissão do dono da view (o bd2), e o dono não passa pela RLS. Sem security_invoker = true, um aluno consultando a view veria o histórico de todo mundo. Com ela, a view lê as tabelas com a permissão de quem consulta, e a política de RLS da seção de segurança é aplicada. Precisa de PostgreSQL 15 ou mais novo.

mv_indicadores e a política de atualização

CREATE MATERIALIZED VIEW IF NOT EXISTS mv_indicadores AS
SELECT pl.periodo_id, d.disciplina_id, ...
       count(*)                                              AS matriculas,
       count(*) FILTER (WHERE h.situacao = 'APROVADO')       AS aprovados,
       round(avg(h.media_final), 2)                          AS media,
       round(100.0 * count(*) FILTER (WHERE h.situacao = 'APROVADO')
             / NULLIF(count(*) FILTER (WHERE h.situacao <> 'CURSANDO'), 0), 1) AS pct_aprovacao
...
GROUP  BY pl.periodo_id, pl.ano, pl.semestre, d.disciplina_id;

-- REFRESH CONCURRENTLY exige um índice ÚNICO na materialized view
CREATE UNIQUE INDEX IF NOT EXISTS uq_mv_indicadores
    ON mv_indicadores (periodo_id, disciplina_id);

-- Depois de cada fechamento de notas:
REFRESH MATERIALIZED VIEW CONCURRENTLY academico.mv_indicadores;
Como funciona
  • Uma linha por disciplina em cada período. O FILTER conta só as linhas que passam na condição, e por isso uma consulta só dá aprovados, reprovados por nota e reprovados por falta.
  • A taxa de aprovação ignora quem ainda está CURSANDO. No semestre corrente todos estão cursando, e o NULLIF(..., 0) transforma o divisor 0 em NULL. Assim o resultado sai NULL em vez de dar erro de divisão por zero.
  • Política: os indicadores só mudam quando a secretaria fecha as notas (A1, A2 e P3). Recalcular a cada consulta ou por gatilho a cada INSERT seria trabalho à toa. A regra é rodar o REFRESH depois de cada fechamento.
  • Por que CONCURRENTLY: o REFRESH normal bloqueia quem está lendo até terminar. O CONCURRENTLY monta o resultado novo ao lado e troca só as linhas que mudaram. É mais lento, mas ninguém fica esperando. Para saber qual linha mudou, ele precisa do índice único.
Pode cair na arguição
  • O que acontece se tirar o security_invoker da vw_historico?
  • Por que não usar uma view comum para os indicadores? E por que não um REFRESH por gatilho?

Índices e EXPLAIN

Frente: Modelagem Física e Desempenho · 05_indices.sql e evidencias/
Pedido: "Criação dos índices, incluindo ao menos um índice parcial" e "Evidências de EXPLAIN (ANALYZE, BUFFERS) antes e depois de cada índice, com o ganho medido".

Os 4 índices

05_indices.sql
-- 1) PARCIAL: só matrícula ativa ocupa vaga (consulta do gatilho e da vw_vagas)
CREATE INDEX IF NOT EXISTS ix_tb_matricula_turma_ativa
    ON tb_matricula_aluno (turma_id)
    WHERE status = 'MATRICULADO';

-- 2) FK do log: FK não ganha índice automático no PostgreSQL
CREATE INDEX IF NOT EXISTS ix_tb_log_matricula_matricula
    ON tb_log_matricula (matricula_aluno_id);

-- 3) EXPRESSÃO: busca de aluno pelo começo do nome, sem ligar para maiúscula
CREATE INDEX IF NOT EXISTS ix_tb_aluno_nome_lower
    ON tb_aluno (lower(nome) text_pattern_ops);

-- 4) Intervalo de datas: relatório de matrículas por dia/semana
CREATE INDEX IF NOT EXISTS ix_tb_matricula_data
    ON tb_matricula_aluno (data_matricula);
Por que cada um

Parcial na turma

O gatilho roda essa contagem em todo INSERT de matrícula. Trancadas e canceladas nunca são contadas, então ficam fora do índice. O índice só é usado quando a consulta também filtra status = 'MATRICULADO'.

FK do log

Serve para "o que aconteceu com esta matrícula?" e para o ON DELETE RESTRICT: antes de apagar uma matrícula, o banco procura log apontando para ela. O log só cresce.

lower(nome)

A consulta compara lower(nome), então o índice tem que guardar lower(nome). O text_pattern_ops compara caractere por caractere e serve para LIKE 'ana%'. Com '%ana' não serve.

Data

A B-tree guarda os valores em ordem, então serve para intervalo (>=, <, BETWEEN), e não só para igualdade.

Como medimos

evidencias/explain_indices.sql (resumo)
BEGIN;
-- massa extra: 100 mil alunos, 300 mil matrículas, 300 mil logs
INSERT INTO tb_aluno ... SELECT ... FROM generate_series(1, 100000) g;
...
ANALYZE;

DROP INDEX ix_tb_matricula_turma_ativa;
EXPLAIN (ANALYZE, BUFFERS) SELECT count(*) FROM tb_matricula_aluno
WHERE turma_id = :turma AND status = 'MATRICULADO';      -- ANTES

CREATE INDEX ix_tb_matricula_turma_ativa ...;
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;                   -- DEPOIS
...
ROLLBACK;   -- a base volta a ser a original
Como funciona
  • Com só 440 matrículas a tabela cabe em poucas páginas, e o planejador prefere ler tudo (Seq Scan). Isso está certo: com pouca linha, o índice não ajuda. Para o índice fazer diferença, o script coloca centenas de milhares de linhas dentro de uma transação, mede, e dá ROLLBACK no fim. Nada fica gravado.
  • ANALYZE dentro do EXPLAIN executa a consulta de verdade e mostra o tempo real. BUFFERS mostra quantas páginas de 8 kB foram lidas. As páginas variam menos que o tempo entre uma execução e outra, por isso usamos elas como prova principal.
  • A saída completa está em evidencias/explain_resultado.txt.

Concorrência: a disputa pela última vaga

Frente: Transações e Concorrência · concorrencia/
Pedido: "Reprodução da anomalia de concorrência na disputa pela última vaga de uma turma; implementação de duas correções distintas, uma por bloqueio explícito, outra por nível de isolamento; comparação fundamentada entre as duas abordagens (custo, contenção, necessidade de retentativa)."

00_preparar.sql cria a turma BD2-DEMO com 1 vaga e zera as matrículas dela. Dois alunos sem matrícula (RA 26000101 e 26000102) tentam entrar ao mesmo tempo, cada um num terminal. Cada script segura a transação aberta por 5 segundos com pg_sleep(5). Essa é a janela em que a outra sessão entra.

1. A anomalia (READ COMMITTED, o padrão)

concorrencia/01_anomalia.sql
BEGIN;   -- READ COMMITTED (padrão)

INSERT INTO tb_matricula_aluno (aluno_id, turma_id)
SELECT a.aluno_id, t.turma_id
FROM   tb_aluno a, tb_turma t
WHERE  a.matricula = :'aluno' AND t.codigo = 'BD2-DEMO';

SELECT pg_sleep(5);
COMMIT;
t
Sessão A (aluno 101)
Sessão B (aluno 102)
t0
INSERT → gatilho conta 0 ocupadas → ok
t1
INSERT → gatilho conta 0 ocupadas → ok
(o INSERT de A ainda não tem COMMIT, então B não enxerga)
t5
COMMIT
t6
COMMIT → 2 alunos para 1 vaga
Por que acontece

O gatilho faz "ler, decidir e gravar": conta as vagas e, se tiver, deixa gravar. Em READ COMMITTED cada comando só enxerga o que já tem COMMIT. A conta de B acontece antes do COMMIT de A, então os dois veem a vaga livre. Contar linhas com SELECT não trava ninguém, e os dois INSERTs são em linhas diferentes. Nada faz B esperar.

2. Correção por bloqueio explícito: FOR UPDATE

concorrencia/02_bloqueio.sql
BEGIN;   -- continua READ COMMITTED

SELECT turma_id, vagas
FROM   tb_turma
WHERE  codigo = 'BD2-DEMO'
FOR UPDATE;            -- trava a linha da turma até o COMMIT

INSERT INTO tb_matricula_aluno (aluno_id, turma_id) ...;
SELECT pg_sleep(5);
COMMIT;

Sessão A
Sessão B
t0
FOR UPDATE na BD2-DEMO → pega a trava
INSERT, conta 0 → ok
t1
FOR UPDATE na BD2-DEMO → espera
t5
COMMIT (solta a trava)
t5
pega a trava → INSERT, conta 1 → "sem vagas"
Como funciona
  • O FOR UPDATE trava só a linha da turma. Quem pedir a mesma trava espera, e matrículas na mesma turma passam a acontecer uma de cada vez. Matrículas em outras turmas não esperam.
  • Quando B finalmente roda o INSERT, a conta dá 1. Em READ COMMITTED cada comando tira uma foto nova dos dados, e o INSERT de B começa depois do COMMIT de A.
  • Ficou no script da sessão para dar para comparar com o 01 sem mexer no gatilho. Num sistema de verdade, o FOR UPDATE iria dentro do fn_tb_valida_vaga, para nenhum programa esquecer de travar.

3. Correção por nível de isolamento: SERIALIZABLE

concorrencia/03_serializable.sql
BEGIN ISOLATION LEVEL SERIALIZABLE;

INSERT INTO tb_matricula_aluno (aluno_id, turma_id) ...;
SELECT pg_sleep(5);
COMMIT;
-- a sessão que perde recebe:
-- ERROR: could not serialize access due to read/write dependencies
--        among transactions   (SQLSTATE 40001)
Como funciona
  • O PostgreSQL garante que o resultado final é igual ao de alguma ordem em fila (A depois B, ou B depois A). Ele não trava a leitura: anota o que cada transação leu. Se A leu algo que B escreveu e B leu algo que A escreveu, cancela uma das duas.
  • Em fila, a segunda veria a primeira e o gatilho recusaria. Como as duas passaram juntas, não existe fila que explique o resultado, e uma é cancelada com 40001.
  • A sessão cancelada precisa ser repetida (retentativa). Na segunda tentativa ela já vê a turma cheia e recebe "sem vagas".
  • Por que não REPEATABLE READ: nele cada transação usa a foto do começo. As duas continuam vendo 0 ocupadas e inserem linhas diferentes. Como não há conflito de escrita na mesma linha, as duas passam (anomalia write skew). Testamos, e deu 2 alunos para 1 vaga.

Comparação e escolha do grupo

FOR UPDATESERIALIZABLE
O que faztrava a linha da turmanão trava; cancela uma transação no conflito
Quem perdeespera e depois recebe "sem vagas"recebe erro 40001 na hora
Retentativanão precisaprecisa: capturar o 40001 e repetir
Contençãofila só na turma disputadaninguém espera, mas no pico muitas transações são canceladas e refeitas
Custoum lock de linha por matrículao banco anota tudo que cada transação lê
Falso positivonão tempode cancelar quem nem disputava a mesma vaga se a leitura não usar índice

Escolha para um sistema de verdade: FOR UPDATE dentro do gatilho. A disputa é sempre pela mesma coisa (a linha da turma) e já sabemos qual linha travar. Ninguém precisa escrever laço de retentativa, e o aluno que perde recebe direto a mensagem certa. O SERIALIZABLE é melhor quando a regra envolve várias tabelas e não dá para saber de antemão o que travar.

Teste extra do falso positivo: duas sessões SERIALIZABLE ao mesmo tempo, uma na BD2-DEMO e outra na RED-N1. As duas deram COMMIT, porque a contagem do gatilho usa o índice parcial, e aí o banco anota só as páginas do índice daquela turma. Aqui o índice da frente de desempenho ajuda também na concorrência.

O gatilho do projeto ficou sem FOR UPDATE de propósito. Com a trava dentro dele, o cenário 01 não conseguiria mais mostrar a anomalia.

  • O que o programa precisa fazer quando recebe o erro 40001?
  • O FOR UPDATE trava a tabela inteira?

Segurança: papéis, GRANT/REVOKE e RLS

Frente: Administração e Operação · 06_seguranca.sql
Pedido: "Papéis de acesso (aluno, secretaria, coordenacao) com GRANT/REVOKE e row-level security" e "RLS impedindo um aluno de ver o histórico de outro".

Papéis e usuários

CREATE ROLE aluno       NOLOGIN;
CREATE ROLE secretaria  NOLOGIN;
CREATE ROLE coordenacao NOLOGIN;

CREATE ROLE aluno_26000001      LOGIN PASSWORD 'aluno'       IN ROLE aluno;
CREATE ROLE usuario_secretaria  LOGIN PASSWORD 'secretaria'  IN ROLE secretaria;
...

Os três papéis são grupos (NOLOGIN): ninguém entra com eles direto. As permissões vão para o grupo, e cada usuário de login entra num grupo. O nome do usuário de aluno é aluno_ + o RA, e é assim que o banco descobre quem está conectado. No script, cada CREATE ROLE fica dentro de um DO que ignora o erro de "já existe", porque CREATE ROLE não tem IF NOT EXISTS.

Primeiro tira tudo, depois dá só o necessário

REVOKE ALL ON SCHEMA academico FROM PUBLIC;
REVOKE ALL ON ALL TABLES IN SCHEMA academico FROM PUBLIC, aluno, secretaria, coordenacao;
GRANT USAGE ON SCHEMA academico TO aluno, secretaria, coordenacao;

-- aluno: catálogo, as próprias linhas (filtradas pela RLS) e as views
GRANT SELECT ON tb_curso, tb_disciplinas, tb_turma, tb_turma_horario, ... TO aluno;
GRANT SELECT ON tb_aluno, tb_matricula_aluno, tb_historico TO aluno;
GRANT SELECT ON vw_oferta, vw_vagas, vw_historico TO aluno;

-- secretaria: lê tudo, escreve aluno, matrícula, nota e log (sem DELETE)
GRANT SELECT ON ALL TABLES IN SCHEMA academico TO secretaria;
GRANT INSERT, UPDATE ON tb_aluno, tb_matricula_aluno, tb_historico TO secretaria;
GRANT INSERT ON tb_log_matricula TO secretaria;

-- coordenacao: lê tudo e monta a oferta
GRANT INSERT, UPDATE, DELETE ON tb_turma, tb_turma_horario, ... TO coordenacao;
Como funciona
  • PUBLIC é "todo mundo que conecta". Tirando dele, um usuário novo não enxerga nada até receber GRANT por algum papel. Isso é o princípio do menor privilégio.
  • USAGE no schema é poder "entrar na pasta". Sem ele, nem o GRANT na tabela adianta.
  • O aluno não recebe tb_professor (tem e-mail), o log nem a mv_indicadores.
  • A secretaria não tem DELETE em matrícula: matrícula se cancela mudando o status, para não perder o histórico e o log.
  • O GRANT decide quais tabelas cada um pode usar e o que pode fazer nelas. A RLS decide quais linhas.

Quem está conectado: fn_aluno_logado()

CREATE OR REPLACE FUNCTION fn_aluno_logado() RETURNS integer
LANGUAGE sql STABLE SECURITY DEFINER
SET search_path = academico, pg_temp
AS $$
    SELECT aluno_id FROM tb_aluno WHERE 'aluno_' || matricula = session_user;
$$;
Como funciona
  • SECURITY DEFINER: a função roda com a permissão do dono (bd2). Ela precisa ler tb_aluno sem passar pela RLS. Se a política de tb_aluno fizesse essa consulta direto, a política chamaria ela mesma.
  • session_user, e não current_user: dentro de uma função SECURITY DEFINER, o current_user vira o dono (bd2). O session_user continua sendo quem fez o login.
  • SET search_path fixo: sem ele, alguém poderia criar uma tb_aluno falsa em outro schema e enganar a função. É a recomendação da documentação para toda função SECURITY DEFINER.

As políticas de RLS

ALTER TABLE tb_historico ENABLE ROW LEVEL SECURITY;

-- tb_historico não tem aluno_id: a política sobe pela matrícula
CREATE POLICY pol_historico_proprio ON tb_historico
    FOR SELECT TO aluno
    USING (EXISTS (SELECT 1
                   FROM   tb_matricula_aluno m
                   WHERE  m.matricula_aluno_id = tb_historico.matricula_aluno_id
                     AND  m.aluno_id = fn_aluno_logado()));

-- secretaria e coordenação veem todas as linhas
CREATE POLICY pol_historico_equipe ON tb_historico
    FOR ALL TO secretaria, coordenacao USING (true) WITH CHECK (true);
Como funciona
  • Com RLS ligada, todo comando na tabela ganha um filtro extra, o USING da política. Quem não tem nenhuma política que libere vê zero linhas. Não dá erro, só volta vazio.
  • O mesmo vale para tb_aluno e tb_matricula_aluno, com aluno_id = fn_aluno_logado().
  • O dono da tabela e o superusuário não passam pela RLS. Por isso conectado como bd2 aparecem as 440 linhas.
  • A vw_vagas não é security_invoker: o aluno vê quantas vagas estão ocupadas em todas as turmas, mas não quem está matriculado.

Backup e restauração

Frente: Administração e Operação · operacao/
Pedido: "Procedimento de backup e restauração, documentado e reproduzível do zero". Na demonstração: "uma restauração de backup ao vivo".

Backup

operacao/backup.sh
DATA=$(date +%Y%m%d_%H%M)
docker compose exec -T postgres pg_dumpall -U bd2 --roles-only > "backups/papeis_$DATA.sql"
docker compose exec -T postgres pg_dump -U bd2 -d matricula -Fc > "backups/matricula_$DATA.dump"
Como funciona
  • Por que dois arquivos: o pg_dump salva um banco, e os papéis (aluno, secretaria...) não pertencem a um banco, pertencem ao servidor inteiro. Sem o papeis.sql, a restauração num servidor novo daria erro em todo GRANT e em toda POLICY, porque os papéis citados não existiriam.
  • -Fc (formato custom): sai compactado, e o pg_restore recria tudo na ordem certa. Também dá para escolher só uma tabela. Um .sql puro só dá para rodar inteiro.
  • A pasta backups/ está no .gitignore: backup não vai para o Git.

Restauração

operacao/restaurar.sh
DUMP=${1:-$(ls -t backups/matricula_*.dump | head -1)}   # o mais recente

docker compose exec -T postgres psql -U bd2 -d postgres -q < "$PAPEIS"
docker compose exec -T postgres dropdb -U bd2 --if-exists --force matricula
docker compose exec -T postgres createdb -U bd2 matricula
docker compose exec -T postgres pg_restore -U bd2 -d matricula < "$DUMP"
# e no fim mostra as contagens: alunos, turmas, matrículas, históricos, políticas
Como funciona
  1. Recria os papéis. No mesmo servidor eles já existem, e o psql só avisa "already exists" (o script filtra esse aviso). Num servidor novo, é aqui que eles são criados.
  2. dropdb --force derruba as conexões abertas (o DBeaver, por exemplo) e apaga o banco.
  3. createdb cria o banco vazio.
  4. pg_restore recria, na ordem certa: extensão, tipos, tabelas, dados, índices, FKs, gatilho, views, RLS, GRANTs e o conteúdo da materialized view.
  5. Mostra as contagens para comparar com as de antes.

Testamos também num servidor novo, vazio, sem os papéis: a restauração funcionou e a RLS continuou valendo.

Pode cair na arguição

  • Qual a vantagem do formato custom sobre o .sql puro?
